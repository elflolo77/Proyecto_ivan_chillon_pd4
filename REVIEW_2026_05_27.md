### Cumplimiento de principios POO (UT1)

En este apartado se valora si el código respeta los principios de encapsulación, herencia y polimorfismo que se trabajaron en la unidad 1, antes de empezar el proyecto. Aquí se han detectado dos puntos importantes.

#### 1. Encapsulación incumplida al cargar datos desde la BD

El repositorio SQLite reconstruye varias entidades del dominio asignando directamente sus atributos protegidos (los que empiezan por guion bajo) desde fuera de la clase. Estos atributos son protegidos precisamente para que solo la propia clase los modifique; al cambiarlos desde fuera te saltas todas las reglas que la clase tiene para protegerse.

Incumplimientos detectados (32 accesos en total, todos en `infrastructure/repositorio_sqlite.py`):

- `_mapear_sesion`: `s._numero_asientos_ocupados`, `s._estado_sesion`.
- `_mapear_entrada`: `e._id_entrada`, `e._fecha_venta`.

**Ejemplo del problema** (`_mapear_sesion`):

```python
s = Sesion(id_sesion, pelicula, sala, fecha_hora)
s._numero_asientos_ocupados = ocupados   # ← acceso directo a protegido
s._estado_sesion = estado                # ← acceso directo a protegido
```

**Por qué importa en tu proyecto.** `Sesion` tiene reglas (no vender entradas si está cancelada, marcar "completa" cuando se llena, no permitir asientos negativos). Esas reglas están implementadas en los métodos `vender_entrada`/`anular_entrada`. Cuando entras "por la puerta de atrás" y pones `s._numero_asientos_ocupados = ocupados`, esas reglas no se aplican: si en la BD hay un dato corrupto con ocupados > capacidad, tu objeto queda en un estado imposible que después romperá `numero_asientos_libres`.

**Cómo resolverlo.** Acepta los datos de la BD en el propio constructor de la entidad, usando parámetros opcionales con valores por defecto. Así la validación se aplica al cargar igual que al crear una sesión nueva:

```python
# En domain/sesion.py
def __init__(self, id_sesion, pelicula, sala, fecha_hora,
             numero_asientos_ocupados=0, estado_sesion="programada"):
    self._id_sesion = id_sesion
    self._pelicula = pelicula
    self._sala = sala
    self._fecha_hora = fecha_hora
    if numero_asientos_ocupados < 0 or numero_asientos_ocupados > sala.capacidad_maxima:
        raise ValueError("Ocupación inválida.")
    if estado_sesion not in ("programada", "completa", "cancelada"):
        raise ValueError("Estado inválido.")
    self._numero_asientos_ocupados = numero_asientos_ocupados
    self._estado_sesion = estado_sesion
```

El repositorio queda sin tocar protegidos:

```python
return Sesion(id_sesion, pelicula, sala, fecha_hora,
              numero_asientos_ocupados=ocupados,
              estado_sesion=estado)
```

El mismo enfoque vale para los demás incumplimientos listados arriba: añade los campos correspondientes como parámetros opcionales al constructor de cada clase (`Entrada` para `_id_entrada` y `_fecha_venta`).

#### 2. Discriminación por tipo en lugar de polimorfismo

El repositorio mira con `isinstance` qué subclase de `Pelicula` recibe para decidir qué hacer con ella. En UT1 vimos que en POO eso lo debe decidir **la propia subclase** sobreescribiendo el método, no quien la usa.

Incumplimientos detectados (24 ocurrencias en total, todas en `infrastructure/repositorio_sqlite.py`):

- `guardar_pelicula`: cadena de `isinstance` sobre `PeliculaComercial` / `PeliculaInfantil` / `PeliculaClasica` para decidir `tipo_pelicula` y qué columna extra rellenar.
- `_mapear_pelicula`: cadena espejo para reconstruir la subclase correcta a partir de la columna `tipo`.

**Ejemplo del problema** (`guardar_pelicula`):

```python
if isinstance(p, PeliculaComercial):
    tipo_pelicula = "COMERCIAL"
    distribuidora = p.distribuidora
elif isinstance(p, PeliculaInfantil):
    tipo_pelicula = "INFANTIL"
    edad_minima = p.edad_minima
elif isinstance(p, PeliculaClasica):
    tipo_pelicula = "CLASICA"
    anio_lanzamiento = p.anio_lanzamiento
```

**Por qué importa en tu proyecto.** Si mañana añades una `PeliculaDocumental`, tienes que recordar tocar este `if/elif`, otro igual en `_mapear_pelicula`, y otro al validar... El conocimiento de "qué tipos de película hay" queda repartido por toda la infraestructura. Si te olvidas de uno, falla en silencio.

**Cómo resolverlo.** Que cada subclase declare en sí misma su tipo y sus campos extra:

```python
# En domain/pelicula.py
class PeliculaComercial(Pelicula):
    TIPO = "COMERCIAL"
    def campos_extra(self):
        return {"distribuidora": self.distribuidora}

class PeliculaInfantil(Pelicula):
    TIPO = "INFANTIL"
    def campos_extra(self):
        return {"edad_minima": self.edad_minima}
```

El repositorio queda sin `isinstance`:

```python
tipo_pelicula = p.TIPO
campos = p.campos_extra()
```

El mismo enfoque vale para el `_mapear_pelicula` espejo: usar un diccionario `{"COMERCIAL": PeliculaComercial, "INFANTIL": PeliculaInfantil, ...}` para elegir la clase y construirla con sus parámetros.

### Cosas que aparecen en tu código y no se han enseñado

1. **Uso de `from contextlib import closing` con dos `with` anidados** dentro del repositorio SQLite (`repositorio_sqlite.py`, método `_ejecutar_consulta`). En clase, y en el proyecto modelo, se ha trabajado con el patrón sencillo:
   ```python
   conn = sqlite3.connect(...)
   try:
       ...
   finally:
       conn.close()
   ```
   El patrón con `closing()` hace lo mismo pero requiere conocer la biblioteca `contextlib`, que no se ha visto en el curso.

2. **Un método "todo en uno" para ejecutar consultas SQL** (`_ejecutar_consulta(query, parametros, fetch_one=False, fetch_all=False, commit=False)`). Es una función que, según los parámetros que se le pasen, se comporta de cuatro maneras distintas (devolver una fila, devolver todas, hacer commit, devolver el número de filas afectadas). El proyecto modelo no tiene nada parecido: cada método del repositorio (`guardar`, `obtener`, `eliminar`...) gestiona su propia conexión y su propio `cursor` de forma directa. Esta abstracción es una decisión de diseño avanzada.

3. **Leer el texto del mensaje de error de SQLite para decidir qué excepción lanzar**:
   ```python
   if "UNIQUE" in str(e):
       raise EntidadDuplicadaError(...)
   elif "FOREIGN KEY" in str(e):
       raise ErrorIntegridadDatos(...)
   ```
   En clase se ha capturado `sqlite3.IntegrityError` y se ha lanzado la excepción de dominio correspondiente, sin mirar dentro del mensaje. Inspeccionar el texto del error es un recurso que no se ha mostrado.

4. **Guardar las tres subclases de `Pelicula` en una sola tabla con una columna que indica el tipo** (`tipo_pelicula = "COMERCIAL" | "INFANTIL" | "CLASICA"`). El proyecto modelo resuelve el mismo problema (dos clases, `Item` e `ItemConDescuento`) de manera **distinta**: dos tablas separadas (`productos` y `descuentos`) y se unen con una segunda consulta. Tu solución es válida, pero es una decisión de diseño que no se ha explicado en clase y que deberías poder justificar.

5. **Reconstruir objetos del dominio asignando directamente sus atributos protegidos desde fuera de la clase**:
   ```python
   s = Sesion(id_sesion, pelicula, sala, fecha_hora)
   s._numero_asientos_ocupados = ocupados
   s._estado_sesion = estado
   ```
   y de forma similar para `Entrada` (`e._id_entrada`, `e._fecha_venta`). En el modelo nunca se hace esto: los objetos se reconstruyen llamando al constructor con todos los datos leídos de la BD. Tocar atributos protegidos de una clase desde fuera salta las protecciones del diseño orientado a objetos que se han trabajado todo el curso.

6. **Una sola plantilla `form_pelicula.html` que sirve para los tres tipos de película**, usando bloques `{% if tipo == "comercial" %} ... {% elif tipo == "infantil" %} ... {% elif tipo == "clasica" %}` para mostrar el campo extra de cada subclase. La plantilla se reutiliza desde tres rutas distintas (`registrar_pelicula_comercial`, `_infantil`, `_clasica`) a través de la función `_render_formulario_pelicula(tipo, ...)`. En clase, y en el proyecto modelo, se trabaja con **una plantilla por operación** (`agregar.html`, `insertar.html`, `comprar.html`, etc.). Reutilizar una plantilla con condicionales Jinja2 es una técnica más avanzada.

7. **Comprobaciones preventivas sobre tipos Python que ya están garantizados**, como por ejemplo:
   ```python
   if not isinstance(fecha_hora_str, str):
       raise ValueError("La fecha debe ser una cadena de texto.")
   ```
   dentro de `programar_sesion`, justo después de recibir un parámetro que ya viene de un `.strip()` en el route (es decir, ya es una cadena con seguridad). Estas validaciones "por si acaso" no se han enseñado en clase y no aparecen en el modelo.
